# Public Live

## OBS and Browser Studio

Live Studio has two modes sharing the same existing Live events and destinations:

- **OBS:** save/publish and enable the event, copy the complete reusable RTMPS address from the admin interface into OBS Server, and leave Stream key empty. Daily broadcasts require no SSH, server start/stop commands or per-event key changes. OBS itself starts/stops the encoder. The server selects the enabled event using the existing live/schedule rules.
- **Browser-Studio:** choose explicitly among today's still-upcoming scheduled livestreams on the Browser Studio screen; the OBS editor's automatically opened row never decides the browser input. If none remain, quick creation opens on the same screen (and can also be chosen manually): enter a required title, optional description and announcement image, then press `Live starten` once. That click uploads the image if selected, saves the new event and starts it. No separate calendar entry or advance date is needed; a missing start time is set automatically on start. Prepare the microphone and optional camera, then choose camera, screen/window, or one of up to 20 local PNG/JPEG/WebP images. Images remain contained, not cropped; the optional camera picture-in-picture can be dragged and resized in the local or separate preview, and a short on-screen title can be added. Microphone/shared-audio gains, a microphone meter and explicit screen-sharing stop are available. Preparation does not transmit. The confirmed start publishes the chosen event and enables its Browser input; no Browser activation checkbox or extra save action is required. OBS selection and activation remain unchanged because OBS connects outside Live Studio.

Browser broadcasting uses a permission-checked, CSRF-protected Laravel WHIP bridge to loopback MediaMTX. The browser never receives OBS/control credentials or MediaMTX's private session resource. Its H264/Opus WebRTC stream is published directly to the canonical `live` path used by the Website. MediaMTX natively remuxes these codecs to HLS and records them as fMP4, so Browser Studio has no intermediate RTSP path, FFmpeg conversion process or second publication hop. OBS continues to use the same canonical path through RTMP/RTMPS, with mutual exclusion enforced by the existing input lock and authorization. Additional destinations still require their existing explicit Publishing selection and real provider authorization.

While the WHIP connection is coming up, the event has an explicit `starting` state instead of being shown as a draft. The public Website switches it to `live` only after MediaMTX reports that the canonical path is available. If WHIP setup fails before that signal, the event's previous publication, mode, time and status are restored. The validated local WHIP resource is stored encrypted and is used only to stop the publisher; it is never returned to the browser after setup.

Only one platform input is accepted while a browser session is active; ready OBS inputs and short OBS authentication reservations prevent a competing browser start. Browser sessions are owned by the initiating publisher. Heartbeats every ten seconds extend a two-minute lease; ending the session, losing publication permission or disabling/unpublishing the event stops the normalization process. Private WHIP resources are encrypted at rest and deleted on explicit termination/relay exit. Window close, Close All and event switching are blocked during an active browser broadcast/recording; disconnects cannot silently restart a new broadcast. Page exit can still lose unsaved local work and cannot guarantee network delivery of cleanup.

Browser output bitrate/encoded-frame counters come from actual `RTCPeerConnection.getStats`, not invented encoder-drop figures. The embedded public preview is detached while browser capture is active to avoid feedback/echo. Native event monitoring continues to show actual Website presence and existing output/recording states; presence is not a proven media-viewer count.

### Audio podcasts without OBS

Prepare a microphone (choose **Ohne Kamera** if desired), explicitly start local audio recording, finish it, then download WAV or save it through the existing resumable Media Library upload. The AudioWorklet records mono PCM from the microphone/shared-audio mix; it is not a fake MediaRecorder MIME conversion. Local recordings are limited to 256 MB (about 46 minutes at 48 kHz) to bound browser memory. Save before closing the window; no background recovery or automatic upload is claimed.

After saving, **Podcast-Entwurf aus gespeichertem Audio erstellen** creates one unpublished Podcast SourceRecord with the original audio usage. Repeating it preserves manual edits; a deleted episode must be explicitly restored. Editing/publishing uses the existing Podcast workspace. For a live audio show, select a cover/image scene and go live with microphone audio; the public stream/replay has that image plus sound.

### Protected server settings and one-time hosting setup

An administrator with `settings.manage` can apply the protected configuration inside Live Studio → Browser-Studio → Server-Einstellungen. The application validates the public hostname, checks the installed MediaMTX binary, refuses on-air reconfiguration, stores an encrypted control secret, validates a candidate config, keeps a private backup and atomically replaces the config. It invokes the existing idempotent subscription-user start script; MediaMTX reloads changed configuration. The validator and start command keep Symfony output pipes enabled so PHP does not open `/dev/null` when the subscription's `open_basedir` excludes it. Failed application restores previous settings/config when possible and explicitly reports unconfirmed rollback. It never runs arbitrary commands supplied by a browser. Configuration outcomes and safe failure metadata (stage, exception type, source location, coded warning and process exit code) are written to private `private/atapin-platform/storage/logs/live-server-configuration.log`; MediaMTX runtime warnings remain in `private/atapin-live/server.log`. Neither log is under the public document root, and configuration contents or control credentials are not logged.

Control API `127.0.0.1:9997`, WHIP HTTP `127.0.0.1:8889` and unencrypted RTMP `127.0.0.1:1935` remain loopback-only. The public HTTP auth handler checks a separate control credential and loopback client IP; API authentication is not excluded. OBS emergency disconnect requires `live.manage`, confirmation and audit, uses the actual RTMP/RTMPS connection endpoint and disables reconnection to the selected event. It cannot stop OBS on the presenter's computer.

The hosting administrator must prepare **once**: existing pinned MediaMTX installation/start task, subscription-user process/config permissions, trusted RTMPS certificate and Website HLS nginx proxy, plus public TCP/UDP **8189** for WebRTC media. API and WHIP HTTP ports must not be opened or publicly proxied. Configure a public reachable WebRTC hostname in the admin interface; private interface addresses are not advertised. PHP-FPM needs at least two workers because MediaMTX authenticates the server-side API/WHIP request through Laravel. The PHP admin has no root authority to install packages, grant firewall privileges or access Plesk certificate private keys automatically.

Screen sharing and shared-audio availability depend on browser/OS permission support; use HTTPS and a current desktop browser. Restricted corporate networks may require a separately installed TURN relay; this release does not install/configure TURN, guests, media-file playback scenes, screen-audio support absent in the OS, or a full OBS mixer. Browser suspension/background throttling can affect canvas frame delivery. Prefer OBS for long/professional productions.

Verification uses synthetic accounts/devices and a real pinned MediaMTX WHIP peer connection on Windows/Edge, WAV/library/draft flows and desktop/mobile screenshots. Linux/Plesk config application, actual RTMPS/provider outputs/firewall and production playback must be smoke-tested on the hosting server before relying on browser broadcasts.

Deploy off-air after a Plesk database backup: receive the code, run the new forward `create_live_browser_sessions` migration with PHP 8.4, clear routes/views, then apply protected settings in the admin interface. Existing OBS keys, recordings and archive URLs are preserved. No new cron services, Composer dependencies or Node production build are required by Browser Studio; completed Live recordings use the existing queue worker for post-processing. Do not use `public:live-config` as an everyday presenter operation.

The navigation displays `Jetzt live` while a published, enabled event has live status; a lightweight `/live/current` check refreshes it every 30 seconds without writing viewer presence. The homepage live card also labels an active event. The `/live` overview embeds the existing HLS player directly in its hero when the selected event is live; scheduled/ended events retain their cover cards. The existing event heartbeat updates both the hero caption and fallback poster and detaches the iframe after the event ends. No new scheduler or MediaMTX configuration is needed.

Completed recordings are processed by the existing queue after MediaMTX closes each segment. The worker remuxes MediaMTX's fMP4 into a seekable MP4 with stream copy and `faststart`; it does not transcode or change the H.264 video or its AAC/Opus audio. The remuxed file is then registered in canonical public storage and the private segment is removed. If FFmpeg is unavailable or the remux fails, the original segment is registered instead and marked as a fallback, so recording ingestion is not lost. A container issue must still be diagnosed against the actual recording (HTTP Range, startup timing, MP4 metadata and codec), not inferred from OBS resolution or duration.

Email reminders use the existing Laravel scheduler and queue (Plesk scheduled PHP tasks); no separate daemon or paid service is installed. Local PHP sendmail is supported with MAIL_MAILER=sendmail and the actual Plesk sendmail path; external SMTP is optional. This is configuration readiness, not proof of server delivery.

- A signed-in visitor opts in on a published future scheduled Live event. Clicking again cancels.
- `public:live-reminders` runs every minute and queues candidates within 15 minutes of starts_at. Time without a zone uses platform.timezone.
- The job rechecks publication, consent and the unchanged event time. Successful SMTP submission is recorded per event time; rescheduling can generate a new reminder. Unique queue locks suppress simultaneous duplicates. SMTP submission is not proof of inbox delivery; mail protocols cannot guarantee exactly-once delivery after a process crash.
- Three job attempts are allowed. A terminal failure is visible and does not restart every minute; cancel/re-enable opts into a retry.
- MAIL_MAILER can be sendmail for local Plesk delivery, or smtp with the deployment's actual MAIL_HOST/MAIL_PORT and authentication/TLS settings. Do not use log/array as real delivery. Store credentials only in the private environment, never Git. If settings change, clear Laravel configuration cache. Local sendmail must be available to the Plesk PHP worker; configuring a path does not verify delivery.
- Existing Plesk scheduler/queue tasks must be enabled. Diagnostic: `/opt/plesk/php/8.4/bin/php platform/artisan public:live-reminders`. The command does not configure SMTP or modify Plesk.

Live chat and page presence refresh every 15 seconds using a CSRF-protected heartbeat. Only published reviewed chat is returned; publication revocations are respected by fresh snapshots. Online counts distinct browser sessions seen within 120 seconds, not proven video viewers. Only a one-way session hash is stored; expired rows are pruned daily. No WebSocket daemon is required.

Web Push uses minishlink/web-push, private encrypted subscriptions and the existing queue. Run `public:push-key` once after migration to generate a stable private VAPID pair (existing pairs are preserved). HTTPS and notification permission are required; signed-in visitors can subscribe/cancel per event and browser. `/public-push-sw.js` only handles notifications; it does not cache private/public pages. Scheduler queues reminders within 15 minutes of starts_at, rechecks publication/time/cancellation, and removes expired subscriptions. Provider acceptance is not proof of notification display. Endpoint hosts are restricted to Google, Mozilla and Apple; redirects are disabled.

Broadcast uses OBS → encrypted RTMPS → MediaMTX → the local HLS player. Open `/desktop` and start `Live Studio` (content.publish permission). Create or select the event that should receive the next broadcast, enable its shared OBS input, and copy the complete private RTMPS server address into OBS Server; leave Stream key empty. The RTMPS path and key are shared by all events, so creating a new title does not require changing OBS. The server selects the enabled event by live status and schedule; after a stream ends, the next scheduled enabled event can receive the same OBS connection. Rotating the shared key invalidates the old OBS address for all events. HLS reading requires explicit public publication. The local RTMP fallback remains on loopback for administrators; only the TLS RTMPS listener is public.

Run public:live-config, then bash platform/bin/live-server.sh install and start as the Plesk subscription user. Installation pins official MediaMTX 1.21.0 and verifies its SHA-256. No Docker, root ownership changes or systemd installation. Start is detached with a lock; status and private/atapin-live/server.log expose process state. Configure a separate Plesk command task to run `/bin/bash /var/www/vhosts/mannavomhimmel.de/httpdocs/platform/bin/live-server.sh start` every minute; the lock makes this safe and it restarts MediaMTX automatically after a reboot. The script does not configure Plesk.

For public RTMPS, the administrator must place the active Plesk certificate chain and its private key at `private/atapin-live/rtmps.crt` and `private/atapin-live/rtmps.key` (or set `LIVE_RTMP_CERT` and `LIVE_RTMP_KEY` in the private platform `.env`). The files must be readable by the subscription user; keep the key mode `0600` and never commit either file. Allow inbound TCP `1936` in the server firewall and use the certificate's DNS name in `LIVE_RTMP_HOST` (default: the `APP_URL` host). Run `public:live-config` again after installing or renewing the certificate. OBS requires a certificate from a public certificate authority; self-signed certificates are rejected by OBS. The streamer does not need SSH or server access after this one-time setup.

Plesk additional nginx directives (owner applies):
```nginx
location /_live/ {
    proxy_pass http://127.0.0.1:8888/;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_redirect / /_live/;
}
```
The SSH tunnel is retained only as an administrative fallback: `ssh -N -L 1935:127.0.0.1:1935 YOUR_PLESK_SSH_USER@mannavomhimmel.de`. Use H.264/AAC and a two-second keyframe interval. The website embeds only `/_live/live/?cookieCheck=1`, not YouTube, and assigns the iframe source only after a successful public HLS manifest probe. When the manifest returns `401` or the event becomes `ended`, the iframe is detached and the branded poster is shown without browser Basic-Auth prompts or an endless player retry loop. MediaMTX hooks update live/ended status and queue completed MP4 segments for remux and Media Library registration. Finished events remain as recordings; they are shown below future/live events and are not selected as the next ingest target. Originals have no automatic expiry while awaiting queue processing; monitor disk usage. Long broadcasts produce multiple one-hour segments, all linked to the event; the ended event page plays the newest completed segment when one exists and shows the poster otherwise. HLS has buffering latency; no server transcoding or paid AI is involved.

AI assistant: Settings → AI has a separate opt-in switch. Signed-in visitors explicitly consent and ask via the AI form (`@Assistent` prefix is accepted there); the existing provider/key/model are reused. The question is sent immediately and its private labelled answer or an error is returned in the same HTTP request, without a queue worker or status polling. Context comes from currently published Website records, active books (public title/description/table of contents), active topics/categories, current navigation, the server clock and only the public-button sections of the synchronized KAI manual. Private complete-edition text, drafts, media originals and credentials are excluded. Each question is limited to 1,000 characters, the provider output to 400 tokens, and the route to 10 requests per minute. There is no application daily limit; use provider-side spending limits as needed. Local tests use Http fakes, never paid requests.
