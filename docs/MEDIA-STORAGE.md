# Файлы и новый импорт Manna Vom Himmel

## Единственное рабочее хранилище бесплатных медиа

Физическая папка: `/var/www/vhosts/mannavomhimmel.de/httpdocs/platform/public/media`.

Файл называется `<SHA-256 содержимого>.<расширение>`. Адрес MP4: `https://mannavomhimmel.de/media/<SHA-256>.mp4`. Это обычный файл в document root; nginx/Apache отдаёт его непосредственно, включая HTTP Range. Симлинки, PHP-передача видео, FFmpeg и очередь оптимизации не используются. Админка, фронтенд, обложки и готовые записи Live получают адрес из одной конфигурации `filesystems.disks.media-canonical`.

Новые обычные/resumable uploads, Takeout, локальные папки/архивы, intake/collector imports и завершённые MP4 Live используют это хранилище для поддерживаемых видео, изображений, аудио и субтитров. Переименование и копирование не меняют содержимое файла. Повторный файл использует тот же физический объект; отдельные источники/загрузки остаются связанными с ним.

Бесплатные бинарные файлы публично адресуемы независимо от статуса редакционного материала — сознательное решение владельца. Статус публикации по-прежнему определяет наличие материала на сайте. Сложное имя не является защитой. Платные PDF, документы, архивы, HTML/CSV/JSON и upload staging остаются приватными. Для платных видео понадобится отдельный защищённый режим до их загрузки: нельзя рассчитывать на блокировку страницы, если сам файл публичен.

Старые private locations поддерживаются для совместимости существующих записей, но Takeout после выполненного владельцем сброса БД не создаёт таких ссылок. Временная архитектура `private/atapin-media/media/objects` и пофайловые ссылки `public/media-videos` больше не используются. Оставшиеся физические старые папки не удаляются программой без отдельного подтверждения.

## Что остаётся в private

- `/var/www/vhosts/mannavomhimmel.de/private/atapin-platform/.env` — вся действующая конфигурация и секреты, без изменений.
- `/var/www/vhosts/mannavomhimmel.de/private/atapin-platform/storage` — logs, cache, sessions, framework и приватные документы/staging. Приватный файловый disk: `/var/www/vhosts/mannavomhimmel.de/private/atapin-platform/storage/app/private`.
- `/var/www/vhosts/mannavomhimmel.de/private/Takeout` — исходная полная распакованная выгрузка Google; не перемещается и не переименовывается.
- `/var/www/vhosts/mannavomhimmel.de/private/youtube_zip_alle` — альтернативный вход multipart Takeout ZIP, если он существует.
- `/var/www/vhosts/mannavomhimmel.de/private/import-inbox` — входы серверного импорта и распаковка архивов; не удалять весь каталог, пока другие импорты могут на него ссылаться.
- `/var/www/vhosts/mannavomhimmel.de/private/manna-intake` — независимый исходный upload archive.
- `/var/www/vhosts/mannavomhimmel.de/private/atapin-live` — MediaMTX runtime, активные записи и секреты. После успешной регистрации завершённый MP4 копируется в public/media, а его временный recording удаляется. Активная трансляция/HLS этим не меняется.
- `/var/www/vhosts/mannavomhimmel.de/private/manna-youtube-runtime` — Python/yt-dlp окружение сборщика; не дубликат Takeout. Старый `private/manna-youtube` удалён владельцем. Default нового входа collector — `private/import-inbox/youtube`; явный `YOUTUBE_ROOT` в сохранённом `.env` имеет приоритет.

Весь private нельзя переносить в document root или открывать симлинком. Новые переменные `.env`, `storage:link`, ручные `mv` файлов Takeout и установка FFmpeg не требуются.

## Импорт одного полного объекта

В Desktop → Import Center → **Google Takeout vom Server** выбрать **Bereits entpackter Export: Takeout** и запустить импорт. Папка уже находится на сервере, повторная загрузка/распаковка не нужна.

1. Импортёр читает небольшой индекс CSV и файлов всех частей. CSV задаёт IDs, тексты, комментарии и связи; HTML-каталог используется для контроля состава. На этом этапе видео не копируются массово.
2. Для текущего видео рассчитывается SHA-256 содержимого, копируются его бинарные файлы и связанные изображения/субтитры с безопасными именами.
3. В короткой транзакции БД записываются видео, metadata/tags, обложки/субтитры, комментарии, Livechat, экспортные настройки и playlist links. Только после полного объекта выставляется checkpoint и начинается следующий.
4. Beiträge обрабатываются аналогично: текст, изображения, poll/Quiz, комментарии и настройки. Остальные контоданные сохраняются приватными редакционными данными. Неизвестные схемы/отсутствующие связи перечислены в отчёте, ничего не угадывается.
5. Не привязанные однозначно бинарные файлы сохраняются как unsorted Media, без выдуманных связей. Длинное экспортное имя не становится физическим именем нового файла. Исходный Takeout сохраняется полностью.

Готовый материал импортируется в `unsorted`, а не публикуется автоматически. Публикация/ручная редактура остаются отдельным действием. Takeout не включает платные ИИ-задачи.

Очередь продолжает работу после закрытия окна. Мягкий бюджет проверяется между целыми объектами; один большой файл может занять дольше. Hash/copy сообщают progress и проверяют stop между блоками. При stop/error частичный временный файл удаляется, исходник остаётся; короткая транзакция откатывает незавершённый объект. Retry не создаёт дубликаты уже завершённых объектов и повторно использует готовые hash-файлы. Папка public/media создаётся автоматически, но пользователь Plesk должен иметь право записи в неё. Требуется свободное место для новой копии медиа сверх сохранённого Takeout.

## Обновление и проверка

Из root SSH получить код, один раз назначить папке media владельца подписки (как у httpdocs), очистить config/views и перезапустить уже загруженный код queue после текущего задания:

```bash
cd /var/www/vhosts/mannavomhimmel.de/httpdocs && \
git pull --ff-only && \
chown --reference=. platform/public/media && \
chmod 0755 platform/public/media && \
/opt/plesk/php/8.4/bin/php platform/artisan config:clear && \
/opt/plesk/php/8.4/bin/php platform/artisan view:clear && \
/opt/plesk/php/8.4/bin/php platform/artisan queue:restart
```

Существующие Plesk PHP 8.4 minute tasks `cron.php schedule` и `cron.php queue` остаются прежними; Composer/Node build/migrations для этой перестройки не нужны. Production не считается проверенным одним push: после обновления используется документированный `bash platform/bin/plesk.sh check`, затем импорт и воспроизведение/перемотка одного опубликованного MP4. В Network его адрес должен начинаться с `/media/`, а Range-запрос получать `206` от веб-сервера. PHP development server не заменяет эту nginx/Apache проверку. Прямой файл устраняет прежнюю PHP-буферизацию; время старта также зависит от самого MP4, соединения и фактической настройки Range веб-сервера.

Внешняя публикация и выбор площадок/restreaming — отдельный согласованный модуль; перестройка хранилища сама по себе не реализует OAuth/YouTube upload/мультистрим.
