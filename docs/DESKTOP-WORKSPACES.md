# Native Desktop workspaces

The Desktop uses the existing Laravel/Blade window shell, database, permissions and queue. No Node production build, second admin shell or mock data is required. Empty lists mean there are no matching records; use **Neu**, search, filters and pagination.

## Available workflows

- **Projekte / Aufgaben:** create and edit projects and tasks, assign staff and deadlines, task board, linked materials/books, paginated related lists. The board operates on the current filtered result page, not every task in the database.
- **Kalender:** month, week and list views combine project/task deadlines, Live events and publication schedules. Times use the configured system timezone and schedules are stored as UTC. Filters narrow large calendars; limits are reported. Scheduling requires a ready material and connected selected destinations. Editing approved content invalidates its scheduled approval; review and schedule again. Cancel stops unclaimed scheduled jobs, not an external publication already completed.
- **Bücher & PDF / Shop:** catalog, author, ISBN, language, public table of contents, separate private complete-edition text, price, projects, topics, cover/sample/full-file attachment, queued PDF generation and paginated sales. The complete-edition text is never rendered on public book pages. Originals are retained. Complete PDF editions must be private; a paid complete edition cannot also be its own sample. Price changes update download roles. PDF rendering uses real Dompdf, bounded text and no remote resources or scripts.
- **Themen & Kategorien:** shared editable taxonomy, active/inactive state, unique slugs and cycle-safe hierarchy. Changes update assigned tags; more than 100 assignments use the queue. A failed refresh can be restarted by saving the term again.
- **Beiträge / Podcast / Videos:** the existing material editor also supports author, project, topics, cover/additional files, SEO, guest, transcript, external Podcast URL and per-platform text. Beiträge support sanitized formatted text and queued PDF editions. Native **Neu** creates an unpublished draft. **Serien** opens episode membership and ordering in the same window; Podcast continues to use SourceRecord/Media, without a parallel model.
- **AI-Assistent / KAI:** interactive admin help and free questions return their private answer or error in the same request without a queue worker. KAI reads the curated `kai_knowledge_entries` database, synchronized from [KAI admin manual](KAI-ADMIN-MANUAL.md) every six hours, plus a fresh read of published Website records, active books and topics. It distinguishes implemented, planned and unverified actions. Long editorial AI suggestions still run in the queue; users review, copy, edit and explicitly apply title/summary/SEO proposals. Disabled AI makes no API call, stale proposals cannot overwrite edits, and KAI has no tools, automatic publishing or secret access. The admin-configured model and `store=false` are retained.
- **Newsletter:** confirmed double-opt-in subscribers, segment tags, search, CSV export, draft editor, preview, explicit send confirmation, scheduled sending and cancellation. Recipient preparation and deliveries run in the queue; each delivery rechecks consent and current staff rights. Sending campaigns are immutable. Failed/uncertain transport attempts are not automatically resent, because delivery may already have occurred. Cancellation cannot recall an in-flight email. Signed opt-out pages use POST for the actual cancellation.
- **Analytik:** actual first-party daily session-deduplicated page/search/download events, playbacks, registrations, current confirmed subscribers and paid sales grouped by currency. Raw search text, IP addresses and private Desktop/account paths are not stored. Reports and CSV require analytics permission. These are not external channel statistics or all-time unique people.
- **Community:** existing moderation remains; the expandable inbox adds imported/local messages, read state, Website replies and queued YouTube comment replies using a real connected account. Only Website messages get Website moderation actions. Imported polls/Live chats do not acquire unsupported external reply APIs.
- **Integrationen:** connection readiness and protected settings links. YouTube/Facebook/Instagram/Telegram/X use the existing real publishing connectors. TikTok/LinkedIn remain profile-only; saving generic Google/Mailchimp/Webhook credentials is not a working API adapter. No invented external analytics is displayed.

## Stripe setup — admin only

1. In **Einstellungen → Integrationen → Stripe**, choose Test or Live mode and save the matching Publishable Key, Secret Key and Webhook Signing Secret. Values are encrypted in the existing settings store, never `.env` or Git. Empty fields preserve saved credentials; secrets are never returned to the browser. The read-only **Verbindung testen** action calls Stripe's account endpoint with the saved Secret Key and records only a safe connected/error status.
2. Copy the exact URL shown in the Stripe settings (production: `https://mannavomhimmel.de/payments/stripe/webhook`) and register it in Stripe for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired` and `charge.refunded`. Use the matching test/live keys and endpoint signing secret. Do not send credentials in chat.
3. Attach a complete private PDF and activate a priced book. Verified users can start a real Stripe Checkout; returning from Checkout does **not** grant access. Only a valid signed webhook with the matching session, amount and currency grants an entitlement. Repeated notifications are idempotent; a full refund revokes that sale's access. Partial refunds do not revoke the complete purchase.
4. Purchased PDF download is authorization-protected and also linked from the customer's account. Archived books remain available to their entitled purchasers.

SMTP/sendmail uses the existing server mail configuration; campaign readiness is reported. External account registration, provider approval, actual payments, SMTP delivery and production playback require owner-side setup and smoke tests. Tests use isolated databases and synthetic fixtures, not real provider calls.

## Applying this release

Back up the existing production database in Plesk before the two forward-compatible migrations. Install the changed Composer lock with Plesk PHP 8.4, migrate, clear cached routes/views and restart existing queue workers. The existing Plesk scheduled task calls `schedule:run`; the new `desktop:dispatch-due` command is registered every minute, so no new cron or systemd service is needed. Keep intake, Takeout and YouTube originals untouched. Run the documented `platform:check` after deployment.
