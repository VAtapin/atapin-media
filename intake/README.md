# Открытый приём файлов — Manna Vom Himmel

Страница **https://mannavomhimmel.de/upload/** без учётной записи, логина или пароля. Этот предварительный этап согласован отдельно от MASTER-ТЗ: владелец может наполнять архив, пока разрабатывается основная платформа.

## Установка в существующий httpdocs на Debian/Plesk

Git уже подключён; корень репозитория находится в `httpdocs`. Поддомен, новый clone, изменение document root и символические ссылки не нужны. Папка `upload` входит в Git, а основной сайт продолжает работать в корне.

В SSH выполните:

```bash
cd /var/www/vhosts/mannavomhimmel.de/httpdocs
git pull --ff-only
bash intake/bin/deploy-plesk.sh
```

Скрипт использует `/opt/plesk/php/8.4/bin/php`. Если у домена в Plesk выбрана другая поддерживаемая версия, задайте её явно, например:

```bash
PLESK_PHP_BIN=/opt/plesk/php/8.3/bin/php bash intake/bin/deploy-plesk.sh
```

Нужны **PHP 8.2+ 64-bit**, расширения **pdo_sqlite** и **fileinfo**, локальная файловая система. Node.js, npm, Composer, MySQL и отдельный процесс на сервере не требуются. Node 22 используется только в автоматических тестах.

Скрипт можно запускать от root или пользователя подписки. При запуске от root он сам выполняет подготовку от владельца `httpdocs`. Он не меняет Git-авторизацию и настройки Plesk. Если `httpdocs` принадлежит root, скрипт остановится: сначала у папки должен быть правильный системный пользователь подписки Plesk.

Что создаётся при первом запуске:

```text
/var/www/vhosts/mannavomhimmel.de/
├── httpdocs/                         # существующий Git-каталог и корень сайта
│   ├── upload/                       # публичная страница и API
│   └── intake/                       # код, интерфейс, команды
└── private/
    ├── manna-intake-config.php        # локальные настройки, вне сайта и Git
    └── manna-intake/                  # архив оригиналов, вне сайта и Git
```

Если архив уже настроен, повторный запуск сохраняет его путь, содержимое, каталог и лимиты. Меняется только разрешённый origin на `https://mannavomhimmel.de`. Прежняя конфигурация `intake/config.local.php`, если она есть, копируется в `private`; существующие оригиналы не перемещаются. Приложение отдаёт предпочтение приватной конфигурации. Для другого основного домена передайте его аргументом: `bash intake/bin/deploy-plesk.sh https://example.com`.

Откройте **https://mannavomhimmel.de/upload/**. Проверка API:

```bash
curl --fail 'https://mannavomhimmel.de/upload/api.php?action=overview' \
  -H 'X-Intake-Request: 1'
```

## Настройки существующего домена в Plesk

Оставьте document root **httpdocs**. У основного домена должен работать HTTPS и PHP-FPM. CLI-версия PHP из команды выше должна соответствовать выбранной версии PHP сайта.

В `upload/.user.ini` уже включены настройки передачи частей:

| Параметр | Значение |
|---|---|
| memory_limit | 128M |
| post_max_size | 8M |
| upload_max_filesize | 8M |
| max_execution_time | 120 |
| max_input_time | 120 |
| display_errors | Off |

Если Plesk задаёт эти параметры как неизменяемые для `.user.ini`, выставьте их в разделе PHP существующего домена. Для `open_basedir` нужен доступ к корню подписки, включая `private`, например `{WEBSPACEROOT}{/}{:}{TMP}{/}` или явно `/var/www/vhosts/mannavomhimmel.de:/tmp`.

Если появляется 413, проверьте лимит тела запроса nginx/Apache: он должен разрешать минимум **8 MB**. Полное видео не передаётся одним запросом — используются части по **4 MiB**. Не добавляйте повторную директиву nginx, если Plesk уже создаёт её в том же контексте.

Справка: [настройки PHP в Plesk](https://docs.plesk.com/en-US/obsidian/administrator-guide/70742/), [ограничения загрузки Apache/nginx](https://support.plesk.com/hc/en-us/articles/12376956284695-How-to-upload-large-files-to-a-website-hosted-in-Plesk). Никакие публичные alias или symlink к `private` не нужны. Оригиналы защищены размещением вне document root, а не правилами `.htaccess`.

## Использование

- Выбирайте сразу несколько файлов или перетаскивайте их в область загрузки. Выбор папок доступен в поддерживающих браузерах.
- Новые файлы можно добавлять, пока предыдущие ещё передаются. Очередь обрабатывается последовательно.
- Есть прогресс, пауза, продолжение и до четырёх автоматических повторов при временном сбое.
- После обновления страницы повторно выберите те же файлы в том же браузере. Принятые части не передаются повторно. При выборе папки повторно выбирайте ту же папку: относительный путь входит в идентификатор возобновления.
- На телефоне держите страницу открытой и устройство активным. Браузер запрашивает удержание экрана, если это поддерживается, но загрузка после закрытия вкладки не обещается.
- На другом устройстве загрузка начинается заново. Повторная отправка уже завершённого файла создаёт отдельный оригинал; одинаковые имена не перезаписываются.
- Имена недавних файлов сохраняются только в браузере отправителя. Общий API отдаёт количества, а не список чужих имён и ссылок на оригиналы.

По умолчанию: **20 GiB на файл, 500 GiB на архив**, с сохранением минимум **2 GiB свободного диска**. Незавершённые файлы также резервируют место. Лимиты можно изменить в `private/manna-intake-config.php`; повторный deploy их сохраняет. Неполные передачи не удаляются автоматически.

## Сортировка и будущая обработка

Оригиналы распределяются в `images`, `video`, `audio`, `documents`, `text`, `archives`, `other`, далее — год/месяц. Принимаются любые расширения, включая HEIC, RAW, MOV, M4A, DOCX, PDF и ZIP, а также пустые файлы. Известное расширение определяет группу; затем используется MIME. Это организационная сортировка, а не антивирус или проверка медиакодека.

Пример: `private/manna-intake/video/2026/09/<id>--recording.mov`. Соседний `<имя>.metadata.json` содержит стабильный ID, исходное имя/путь, размер, время, MIME, категорию и SHA-256 каждой принятой части. Исходное имя очищается для файловой системы и при необходимости сокращается; полное имя остаётся в метаданных.

Архивы не распаковываются. Нет публичных endpoint для скачивания, удаления или исполнения оригиналов. Файлы пока не обрабатываются AI и не публикуются: будущий импортёр Media Library сможет читать их метаданные.

## Обновление и обслуживание

Обновление выполняется теми же тремя командами `cd`, `git pull --ff-only`, `bash intake/bin/deploy-plesk.sh`. Исходники и архив независимы. Если в OPcache отключена проверка изменения PHP-файлов, после обновления перезапустите PHP-FPM домена через Plesk.

От пользователя подписки (либо через `runuser -u ИМЯ_ПОЛЬЗОВАТЕЛЯ -- ...` из root):

```bash
cd /var/www/vhosts/mannavomhimmel.de/httpdocs
/opt/plesk/php/8.4/bin/php intake/bin/console.php status
/opt/plesk/php/8.4/bin/php intake/bin/console.php verify
```

`verify` читает готовые оригиналы и проверяет контрольные суммы всех частей. Эта команда ничего не изменяет, но может долго работать на большом архиве.

Включите приватную конфигурацию и архив в резервное копирование. Для согласованного снимка SQLite используйте `console.php backup-catalogue /абсолютный/новый-файл.sqlite`; он не заменяет копию оригиналов и `.metadata.json`. Для полного согласованного бэкапа используйте снимок файловой системы/Plesk или временно остановите приём во время копирования.

## Проверки разработчика

```bash
php intake/tests/archive.php
node intake/tests/http.mjs
node intake/tests/subfolder.mjs
```

GitHub Actions использует Linux, PHP 8.2/8.4 и Node 22. Проверяется настоящий PHP-сервер: загрузка частей, повтор после потери ответа, целостность оригинала, приватность хранилища, запуск из существующего `httpdocs`, повторный deploy, мобильный и настольный браузер. Тест подпапки запускается на Linux, а в CI дополнительно проверяет переключение с root на владельца сайта.

Оформление продолжает `UI/approved/`: navy, gold, кремовые поверхности, Playfair Display и Inter. Шрифты размещены локально. Немецкие тексты отделены в `lang/de.php` и `public/lang-de.js`.
